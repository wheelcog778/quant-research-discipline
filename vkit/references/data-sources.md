# A 股数据：多源抓取、自建复权、大样本审计

> 实测记录。换标的（美股/期货/加密）时，抓取部分失效，但复权与审计工程形态仍然适用。

---

## 1. 数据源降级顺序（实测）

| 源 | 单只上限 | 复权 | 成交额 | 限流表现 |
|---|---|---|---|---|
| 东财 push2his `fqt=2` | 2500 根 | 后复权 | ✅ | **连续 33 页翻页后整段 IP 被封，40 分钟未恢复** |
| 新浪 `CN_MarketData` | 1500 根 | 不复权 | ❌ | 前 5 分钟 64 只/分，之后掉到 12 只/分，过一阵恢复 105 只/分 |
| 腾讯 `fqkline` `qfqday` | 640 根 | 前复权 | ❌ | 稳定，无封禁；字段名是 `qfqday` 不是 `qfq` |

**实践顺序**：腾讯（稳、前复权、2.6 年）→ 新浪（6 年、需自建复权、会限流）→ 东财（质量最好但要限速到很慢）。

---

## 2. 自建复权（不复权源必做）

A 股主板常规交易日涨跌幅通常为 ±10%，所以：

> 深于约 −11.5% 的跳空，**可能**是除权，也可能是无涨跌幅限制、复牌、异常行情或坏数据。
> 不能仅凭阈值自动认定除权并缩放；必须结合公告、股本变动和第二个数据源交叉验证。

实测：3018 只里检出 **1156 个**这样的点，平均每股 0.38 次。
只做阈值判断的"自建复权"会把真实异常行情误当除权，必须先分类再决定是否调整；
不做这一步，形态计算又会被假暴跌污染——所有"跌破 MA20""急跌"判据都会误触发。

**分红除息（2–5%）检测不到**，会留下小跳空。所以必须用另一个源交叉验证：
同向、同量级才算过。

验证记录：新浪（自建复权）与腾讯（前复权）两个独立源，5 日 IC −0.022 vs −0.029，
分类方向一致 → 结论不依赖复权实现的细节。

## 3. 大样本审计的工程形态

400 万条观测不能塞进内存。可用形态：**两阶段**

```
阶段一（--build）：逐股逐日复算 → SQLite(date, sym, score, cat, fwd1/5/10/20, regime)
阶段二（--stats）：SELECT ... WHERE date=? 逐日取出 → 算 IC/分档 → 丢弃
```

- **SQLite 比 CSV 好**：可断点续跑（`meta.done` 记录已完成股票）、可直接按日分组查询。
- 前向收益在阶段一就算好写进表，阶段二不再需要价格面板 → **内存恒定**。
- 实测：3018 只 × 1439 天复算约 11 分钟，统计约 3 分钟，库约 450MB。

## 4. 抓取失败的处理

实测：3052 只里 33 只没抓到，**全部是"仅 N 根"（上市不足 250 个交易日的新股），没有一例网络失败**。

这很关键：缺口只影响近期上市的新股。但**这不等于没有偏差**——如果目标投资域包含新股，系统性排除它们仍然改变了样本。正确处理是把它写成一个明确的 universe 限制，并在报告口径里声明。
判据：把失败清单逐条看一遍，区分"数据源没给"和"这个标的本来就没有足够历史"。
前者要重试，后者要在报告里写明为 universe 限制。

## 5. 三个容易忽略的口径

1. **成交量单位**：新浪是股，东财是手。只用量比时无所谓，但要算成交额就必须统一。
2. **成交额缺失**：新浪日 K 没有成交额，VWAP 只能用 `(H+L+2C)/4` 估算。
   如果要判"分时四维"（上影、收盘位置、振幅），日 K 根本不够——**需要分钟数据**。
   在日 K 上做这类判断，等于用收盘后才知道的信息判断盘中，回测会系统性高估。
3. **幸存者偏差**：样本只含当前仍在交易的股票时，正向信号会被高估。
   **不要假设负向结论天然稳健**——方向取决于因子结构与退市机制，无法预先判定。
   做法：纳入历史退市样本，或至少给出敏感性分析与适用边界。

## 6. 审计库的字段设计

最小可用字段集（少一个就会在第二阶段卡住）：

| 字段 | 用途 |
|---|---|
| `date` | 分组键，必须与交易日历对齐 |
| `sym` / `code` | 标的 |
| `score` | 因子值，IC 的输入 |
| `cat` | 分类标签，用于分类超额与标签回查 |
| `fwd1/5/10/20` | 前向收益，阶段二复用，避免重复读价格 |
| `regime` | 市场状态，用于分 regime 检验 |
| `vwap_real` | 该日 VWAP 是否为真实值（1/0），用于数据质量分层 |

**建议再加一列 `flags`**（JSON 或位图）：记录该观测是否成交、是否停牌、是否涨跌停封板。
本案例缺这一列，导致"买不进"的情况只能事后推断。

## 7. 配套的本地审计库（直接回灌 vkit）

`~/.product/cache/history_2y/`（Windows：`C:\Users\the author\.product\cache\history_2y\`），约 **1.4GB**：

| 文件 | 内容 |
|---|---|
| `audit_sina6y_loose.db` / `_strict.db` | 各 **410.3 万行**，3018 只 × 1439 交易日（2020-11-20 起），列 `date,sym,score,cat,fwd1/5/10/20,regime,vwap_real`；`meta.done` 是可续跑名单 |
| `k_<sym>.json`（3018 个） | 新浪后复权日 K：`open/high/low/close/volume`，`amount` 为 null |
| `bench_sh000300.json` | 沪深 300，用于 `timing` |

回灌一条命令：

```bash
python examples/export_from_db.py --db <cache>/audit_sina6y_loose.db \
    --bars-json <cache> --out /tmp/real200 --max-codes 200 --hold 20
# → bars/ factor.csv signals.csv rows.csv index.csv，再接 ic / conc / timing / sim
```

三个坑：

1. **它是审计结果表，不是行情库。** `ic` 仍要从 `k_*.json` 建 bars 自己算前向收益——顺便把算出来的 fwd 和库里的 `fwd*` 对一遍，这是免费的交叉验证。
2. **`signals.csv` 默认导出全部行。** 拿它跑 `timing` 等于「几乎每天都有信号 vs 极少天无信号」，差值（实测 −2 到 −3pp）是定义出来的，不是市场给的。按 `cat` 分开导出（`risk` / `reversal` / `momentum`）再跑。
3. **先估内存再跑全量。** 百万行级别的 `factor.csv` 会被 `ic` 整个读进内存；本机可用内存只有 2GB 时，200 只子集（约 28 万观测、16 秒）是安全档。报告里写明是全池还是子集。
